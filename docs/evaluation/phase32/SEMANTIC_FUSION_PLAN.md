## 1. 결론과 이번 목표

권장 방향은 검색별 상위 후보를 보존하고, 검색 결과에서 Entry당 2개를
강제로 삭제하는 규칙을 제거하는 것이다. 근거 조각 수와 화면의 카드 수는
다른 문제다. 한 Entry의 여러 조각이 답을 뒷받침하면 함께 검색할 수 있어야 한다.
화면에서 같은 Entry를 묶는 작업은 이후 B2에서 검토한다.

다만 새 혼합 방식이 의미 검색 단독보다 좋은지도 같은 조건에서 비교한다.
혼합이라는 이유로 더 나은 방식을 미리 가정하지 않는다. 이번 결과는 새
검증을 통과한 규칙 하나, 또는 다음에 해결해야 할 실패 원인으로 끝낸다.

## 2. 실제 관찰과 가설을 구분한다

앞 차수는 탐색에서 B를 선택한 뒤 별도 검증에서 실패했다.
검증용 8개 중 단어 검색 5개, 의미 검색 7개, 고정 B 혼합 5개의 완전 근거를 찾았다.

| 사례 | 관찰 | 이번에 검증할 문제 |
| --- | --- | --- |
| valid-03 | 의미 2위 → 제한 전 혼합 21위 → 최종 제한에서도 제외 | 한 검색에서만 강한 후보가 혼합에서 밀림 |
| valid-05 | 의미 중복 그룹화 후 36위 / 제한 전 혼합 59위 | 후보 순위 자체가 낮음; 제한 제거만으로 해결되지 않음 |
| valid-06 | 단어 9위 / 의미 2위 / 제한 전 혼합 3위 → 최종 제한으로 제외 | 유효한 근거가 마지막 삭제 규칙에서 빠짐 |

`valid-03`의 밀림이 모두 무관한 결과 때문이라고 단정하지 않는다.
상위 후보의 순위 기여와 양쪽 검색 등장 여부를 기록하고, 선택된 비정답
후보를 소량 발췌해 관련성·근거 여부를 따로 확인한다. 관련 문장과 정답을
직접 뒷받침하는 문장은 구분한다.

고정 가중치 RRF는 두 검색에 함께 등장한 후보의 점수를 합산한다.
한 검색에서 높은 순위라는 이유만으로 최종 상위 결과가 보장되지는 않는다.
이것이 실패에 기여한 정도를 기존 저장 순위로 분리해 확인한다.

## 3. 유지할 조건과 데이터

- 모델 small/1536차원, `sections-600-v1`, 원문 범위와 부모 hash를 유지한다.
- 같은 허용된 43개 문서, 질문별 기존 필터, 검색별 후보 100개 / 최종 결과 20개.
- 정확 중복 그룹화는 후보 제한 전에 수행한다. 근사 중복 제거는 추가하지 않는다.
- RRF 상수 60, 동등한 가중치와 결정적인 동점 순서를 유지한다.
- 정답·Entry ID·질문 언어를 순위 생성이나 보호 대상 선택에 사용하지 않는다.
- 완전한 동일 버전의 근거 범위를 덮어야 성공이라는 채점 기준을 유지한다.
- 기존 데이터셋·capture·보고서·freeze는 덮어쓰지 않는다.

기존 20문항은 이제 모두 조정 자료다. 18개 지원 사례와 근거 부족 2개를
보존하되, 앞 검증 10개를 다시 독립 검증이라고 부르지 않는다. 두 저장 순위를
각자의 dataset digest에 연결한 채 결과만 합산하며, dataset을 합치거나 새
digest로 바꿔 원래 capture의 소유자·근거 검사를 우회하지 않는다.

## 4. 사전에 고정할 네 비교

모든 비교는 후보 단계의 Entry 제한을 제거한 동일한 두 후보 목록을 쓴다.

| 이름 | 최종 선택 규칙 | 목적 |
| --- | --- | --- |
| B0 | 기존 RRF + 최종 Entry당 2개 | 앞 차수 B 재현 기준 |
| R | 기존 RRF, 최종 Entry 제한 제거 | 마지막 삭제 규칙의 효과 분리 |
| P: 우선 권장안 | 검색별 상위 5개 그룹 보존 후 RRF로 채움, Entry 제한 없음 | 강한 단어/의미 후보의 밀림 방지 |
| S | 의미 검색 상위 20개, Entry 제한 없음 | 혼합이 단독 검색보다 유용한지 비교 |

P의 정확한 동작:

1. 그룹화된 단어 후보 상위 5개와 의미 후보 상위 5개의 합집합을 구한다.
2. 이 최대 10개 보호 그룹을 같은 RRF 점수와 동점 순서로 먼저 배치한다.
3. 보호 그룹 밖의 후보를 기존 RRF 순서로 추가해 최대 20개를 채운다.
4. 결과에는 같은 그룹을 한 번만 넣고, 각 그룹의 유효한 원문 위치는 합집합으로 보존한다.
5. 한쪽 후보가 비어도 동작하며, 부족한 보호 슬롯을 만들기 위해 낮은 후보를 추가하지 않는다.

5개는 최종 20개 중 최대 절반을 양쪽 검색의 상위 후보에 배정한다는 설계값이다.
이번 차수에서는 3/5/10 등을 반복 탐색하지 않는다. 보호 후보도 부적절할 수 있고,
좋은 RRF 후보를 뒤로 밀 수 있으므로 @5/10과 후보 원문을 함께 검토한다.

R은 앞 차수 D와 같은 순위 의미이므로 재현을 확인한다. S도 기존 B의 의미
목록을 재현한다. 이미 관찰한 성공을 새로운 독립 검증 성공으로 표시하지 않는다.

문서 계열 다양성은 별도로 보고한다. snapshot은 같은 경로로 묶고, 알려진
번역 경로의 계열 매핑을 private protocol에 먼저 고정한다. 이것은 진단용이며
새 계열 제한이나 다양성 가산점을 순위에 추가하지 않는다.

## 5. 최소 구현 범위

1. 기존 capture를 검증하는 경로와 새 순위 규칙 설정을 분리한다.
   `load_capture`는 원래 schema/rule digest와 현재 owner/DB/corpus/policy를
   계속 검사한다. 기존 `RULES`/`RULE_DIGEST`를 바꾸어 저장 파일을 거부하거나
   재해석하지 않는다. 새 보고서는 입력 capture digest와 새 규칙 digest를 함께 기록한다.
2. 원래 A 재현 검사를 먼저 통과한 후 B0/R/P/S를 재생한다.
3. 그룹 대표 선택을 고정하고 두 후보의 alias 위치를 결정적으로 합친다.
   기존 B0 결과와 다르면 먼저 원인을 설명한다. 조용히 채점 의미를 바꾸지 않는다.
4. 각 후보의 단어/의미 순위, 각 RRF 기여, 보호 여부, 최종 순위와 제외 이유를
   저장한다. 보고서에는 질문·정답·본문·벡터를 넣지 않는다.
5. 선택/고정/검증 함수를 새 규칙 설정에 맞게 확장한다. 이전 freeze 검증도 유지한다.
6. 합성 테스트로 보호 그룹 보존, 중복·alias 합집합, 동점, 한쪽 빈 후보,
   한 Entry의 세 조각, 최대 20개, stale/권한 거절과 API 호출 0회를 확인한다.

새 DB 테이블, migration, worker, 의존성, 제품 검색 API/UI는 필요하지 않다.
이 단계에서는 구현과 로컬 조정만 수행할 수 있으며 API 비용은 0이다.

## 6. 조정에서 선택할 조건

기존 18개 지원 사례에서 B0/R/P/S를 비교하고, 근거 부족 2개는 recall 분모에서 제외한다.
다음 조건을 만족하는 R/P/S 중 하나를 고른다.

- 평균 group recall@20 ≥ 0.80, 모든 필수 근거 발견 비율 ≥ 0.70.
- 같은 후보 범위에서 단어 검색 성공을 모두 유지한다.
- 단어 검색이 놓친 한국어 사례를 최소 1개 추가 회복한다.
- B0에서 @5 또는 @10에 완전 근거를 찾았던 사례의 손실은 각 단계에서 최대 1개.
  손실 사례의 전후 순위를 사용자에게 별도로 보여준다.

선택 순서는 recall@20 → 완전 근거 비율 → recall@10 → recall@5다.
모두 같으면 변화가 작은 R → P → S 순으로 선택한다. P를 우선 제안하되
측정 전에 선택하거나 S를 혼합 방식의 실패를 가리는 대조 조건으로만 취급하지 않는다.
S가 선택되면 의미 검색 단독이 B2 후보라는 점을 명시하고 제품 모드 범위도 함께 설명한다.

적격 조건이 없으면 이 차수를 종료한다. 가중치·모델·문단 크기·보호 개수를
바꿔 통과할 때까지 반복하지 않는다. 특정 실패 사례가 해결돼도 전체 기준을
통과했다고 표현하지 않는다. `valid-05`처럼 처음 순위가 낮은 사례는 따로 남긴다.

## 7. 새 독립 검증과 전송 확인

새 검증 세트는 지원 질문 8개 + 근거 부족 2개를 목표로 한다.
지원 사례에는 한국어→영어 문서 질문과 영어 질문이 각각 최소 3개,
최소 3개 문서 계열이 있어야 한다. 가능하면 기존 조정에서 근거로 사용하지
않았던 출시 절차·코스 미리보기·타이머 오디오 문서 등을 먼저 검토한다.
같은 사실의 번역·다른 snapshot·바꿔쓰기 질문은 새 독립 사례로 인정하지 않는다.
문서 경로가 달라도 같은 사실이면 제외한다. 충분한 새 사실이 없으면 범위
부족을 보고하고 추가 자료를 제안하며, 억지로 10개를 만들지 않는다.

선택 조건을 먼저 고정하고, 새 규칙의 조정 점수를 열기 전에 새 검증 질문을
준비한다. 에이전트가 질문·정답·정확한 근거 후보와 조정 사례와의 중복 검토표를
만든다. 사용자는 유용성과 직접 지원 여부를 모아서 확인한다. 승인된 새
dataset을 먼저 고정한 뒤 기존 20문항으로 규칙을 선택한다. 새 검증 질문의
검색 품질은 선택 완료 전 측정하지 않는다. 선택 후 규칙과 해당
dataset/config/corpus digest를 freeze한다. 결과에 유리한 새 질문을 뒤늦게
고르는 것을 막기 위한 순서다.

전송 전에 한 번의 새 capture에 필요한 실제 문서 ID/조각 수, 새 질문 목록과
fresh manifest 비용을 보여주고 승인받는다. 직전 허용은 이미 완료된 두 실험에
대한 것이므로 새 질문·새 실행에 재사용하지 않는다. DB에 남아 있는 AI 허용도
이번 실행 승인과 구분한다. 같은 43개 문서라도 벡터는 저장하지 않았으므로
새 질문을 비교하려면 문서 재임베딩 비용이 들 수 있다.
실행당 USD 0.01을 우선 제안하고, fresh estimate가 초과하면 실행 전에 확인한다.
새 외부 전송이 승인되지 않아도 로컬 조정 결과와 제한은 전달할 수 있다.

새 독립 검증에는 같은 0.80/0.70, 단어 검색 성공 유지, 한국어 추가 회복 기준을
적용한다. @5/@10의 B0 성공 손실 제한도 동일하게 적용해 상위 사용성을 확인한다.
선택한 규칙과 B0를 같은 새 capture로 비교하며, 결과를 보고 다른 후보를
새로 선택하지 않는다. 근거 부족 사례는 관련 후보가 있어도 정답으로 승인하지
않으며, 답변 보류·환각 검증은 아직 Phase 3.3의 일이다.

검증에 실패하면 실패 보고서를 보존하고 B2를 보류한다. 검증을 통과하면
선택한 규칙과 실제 검색 화면 범위를 사용자에게 보여준 다음 B2 진행을 확인한다.
이 계획 승인만으로 pgvector나 브라우저 의미 검색을 구현하지 않는다.

## 8. 순서와 확인 지점

1. 도구와 합성 테스트 구현, 새 질문 초안 준비 → 사용자 질문/근거 확인과 dataset 고정.
2. 기존 20문항 로컬 비교 → 비교표·손실 사례·후보 문장 검토 결과 보고, 후보 하나 고정.
   여기까지 외부 API 호출 0회다.
3. 새 전송 범위·fresh manifest 비용 승인 → 승인한 새 capture 한 번 실행.
4. 고정 후보 검증 → 통과/실패, 비용/지연과 누락 이유 보고.
5. 통과한 경우에만 B2의 검색 모드, 원문 읽기와 사용자 확인 흐름 제안.

완료 보고에는 바뀔 규칙, 순위가 보호되거나 밀린 이유, 조정/독립 검증의 차이,
@5/10/20 점수, 남은 실패와 제품 적용 시점을 적는다. 사용자가 근거를 다시
찾는 작업을 맡지 않도록 실패 사례의 승인된 근거와 후보를 함께 보여준다.
