## 실행 체크포인트: 4,096 후보의 로컬 구현 완료 (2026-10-19)

사용자가 “일반 답변의 출력 상한을 4,096토큰 후보로 두고 로컬 구현을 이어가줘”로
상한 후보 변경과 로컬 구현을 명시했다. 아래 첫 512 게이트의 실패 기록은 보존한다.
이는 Luna의 실제 출력 용량 통과나 외부 AI 전송·과금 승인이 아니다.

- 일반 답변만 `claim-evidence-v1`로 연결했다. 요청 부분 1–3/주장 0–6/총 근거
  참조 최대 8/미확인 최대 3개를 검증한다. 인용 구절은 실제 전송한 본문 내 정확한
  부분 문자열이어야 한다. 잘못된 형식·구절·완료 선언은 자르거나 보정하지 않고 거부한다.
- 직접 답/관련 진행의 문장과 미확인 문장을 순서대로 조립하고, 표시한 주장에 쓰인
  출처만 반환한다. 배경만 있으면 고정 범위 안내와 빈 인용의 insufficient다.
  고정 안내는 한국어 질문에 한국어, 그 밖에는 영어다. 다른 언어의 고정 안내는 미지원이다.
  모델이 직접 답/진행을 잘못 분류하거나 요청 부분/중요 사실을 빠뜨리는 의미 오류까지
  증명하지 못한다. 실제 모델의 의미/인용/v1 필수 항목 검토는 여전히 필요하다.
- 일반 출력 상한 4,096, 회고/과거는 기존 schema·지침·512를 유지한다. 모드는 명시하며
  구형 일반 형식을 자동 수용하지 않는다. 공개 API 응답 필드는 유지하고 일반 상태 조회의
  출력 상한과 생성 OpenAPI 타입을 갱신했다. 화면은 조립 문장의 줄바꿈을 보존한다.
- 과금 예약·사용량 검증은 실제 요청의 상한을 사용한다. 회고/과거 512와 일반 4,096의
  저장된 예약액을 합성 DB/API 검사로 확인했다. 이전 과금 행을 재계산하지 않는다.
  새 config hash `1a3d99a150b7d3c6dd79e3cf3df7156f9546ffe57022f6ee8ac5e0c9fa5f1c66`로
  기존 승인/준비물의 재사용을 막는다. 건별 USD 0.01 제한은 그대로다.
- 기존 일반 5문맥의 질문/본문/메타데이터 입력을 보존했다. 실제 새 요청은
  **8,075–14,230 bytes**이고 회고/과거 2요청은 기존과 완전히 동일하다.
  같은 7건의 계산상 예약 합계는 **USD 0.019314**다. 승인된 실행 제안은 아니며,
  전용 실행기·요청 digest·중단 조건을 고정한 후 별도 유료 승인을 받아야 한다.
- 검증: 전체 백엔드 **818개**, 관련 프론트 **61개**, lint/build 및 공백 검사 통과.
  실제 모델 schema 수용/4,096 출력 용량/의미 품질/자동 검색 완료 검증은 미실행이다.
- 보존 대조: 기존 **524파일/471과금 행**, 권한/현재 버전/1,097 anchor 동일.
  미확정 **3건/USD 0.006801** 유지. 신규 AI 호출/과금 0, ANSWER_MODE=off.
  Phase 3.3 미완료, Phase 4 미착수. 프로젝트 의존성/DB 스키마 변경은 없다.

## 실행 체크포인트: 첫 크기 게이트 검토 완료 (2026-10-19)

계획대로 오프라인 계약 후보와 검사 도구를 만들었다. **입력 통과 / 출력 미통과**로
이하 제품 연결·parser/조립기 구현·새 유료 제안으로 넘어가지 않았다.

- 기존 일반 5문맥을 그대로 보존했고 새 요청은 8,077–14,232 bytes로 14 KiB 이하다.
  질문·원문·메타데이터의 직렬화 입력 digest가 기존과 일치한다. 실제 schema 수용은
  아직 모델에 시험하지 않았다. 기존 v1 체크리스트를 확장 표로 기록했으며 기준 변경은 없다.
- 합성 출력은 참고 인코딩 `o200k_base`에서 짧은 partial 103토큰, 최대 필드 조합
  1,493토큰이었다. 임시 설치한 tiktoken 0.14.0에 `gpt-6-luna` 매핑이 없어 이 값을
  Luna의 정확한 토큰 수로 주장하지 않는다. 512토큰 수용을 검증하지 못했으므로
  게이트를 통과 처리하지 않았다. 문자수/4 추정이나 원문 절단으로 우회하지 않았다.
- 일반 출력 512/2,048/4,096 후보의 7건 계산상 예약 합계는 각각 USD 0.010355 /
  0.014195 / 0.019315다. 회고/과거는 512를 유지한 산술 비교이며 새 실행 제안/승인,
  토큰 용량 보증이나 실제 비용 예측이 아니다. 어느 값도 설정에 적용하지 않았다.
- 권장 검토 방향: 문맥/필수 내용을 임의로 줄이는 대신 **일반 출력 4,096 후보의
  명시적 범위 변경**을 검토한다. 2,048 대비 총 예약 차이는 USD 0.005120이다.
  대안은 구조/근거 구절의 중복을 줄인 새 계약을 먼저 설계하고 크기를 재검사하는 것이다.
  원래 ‘자동 상향하지 않는다’ 조건은 유지한다. 선택이 확정되기 전에는 런타임을 바꾸지 않는다.
- 새 순수 용량 검사 3개 및 전체 백엔드 **778개 통과**, CLI 도움말·공백 검사 통과.
  실제 답변/공개 API/UI는 바뀌지 않아 프론트 표시 테스트 단계는 아직 해당하지 않는다.
- 보존 대조: 기존 419개 파일, 471개 과금 행, 권한/현재 버전, 1,097 anchor 동일.
  기존 미확정 3건/USD 0.006801 유지. AI 호출/새 과금 0, ANSWER_MODE=off.
  임시 토크나이저는 `/private/tmp`에만 설치했고 프로젝트 의존성은 추가하지 않았다.

## 1. 목표와 고정 경계

사용자가 기록을 질문하면, 질문에 답하는 사실과 확인된 진행을 해당 원문에 연결해
알려주고, 확인되지 않은 결과는 범위를 한정해 표시한다. 직접 관련된 사실/진행이
없으면 근거 부족을 표시한다. 최종 결과가 AI 대화 밖에서 결정됐을 가능성을 인정한다.

이번 작업은 **일반 답변의 내부 생성 계약**에 한정한다. 모델 교체·다단계 AI 심판·
검색 순위/추천 변경·자료 추가·인덱싱·권한 확대는 포함하지 않는다. 날짜 회고와
과거 시점 답변은 현재 형식/동작을 유지하고 모드별 회귀를 확인한다. Phase 4는
시작하지 않는다. 공개 API의 status/answer/citations/policy_revision 형태는 유지한다.

ANSWER_MODE=off, Luna 기본 모델, 일반 제품의 건별 USD 0.01 제한, 최대 5근거/
14 KiB 요청을 유지한다. 기존 원본/평가/미확정 과금 3건 USD 0.006801을 보존한다.
유료 검증 승인은 모두 종료됐으며 이 계획이나 리뷰 호출은 답변 재실행을 허용하지 않는다.

## 2. 실패별 목표와 평가 기준 정리

| 남은 문제 | 구현이 드러내야 할 정보 | 여전히 직접 판정할 항목 |
| --- | --- | --- |
| 관련 진행 누락 | 질문의 각 요청 부분, 회수한 사실/진행, 미확인 결과의 연결 | 중요한 알려진 진행을 모델이 누락했는지 |
| 주장·인용 불일치 | 주장마다 실제 제공 원문 ID와 근거 구절 | 구절이 주장 전체를 뒷받침하는지, 귀속/조건이 맞는지 |
| 배경을 직접 근거로 오인 | 직접 답/직접 진행/배경의 구분 | 해당 배경이 요청 결과의 증거인지 |

기존 7건의 질문·필수 사실·미확인 범위·원본 판정을 v1로 동결한다. 새 결과도 같은
기준으로 채점하며, 구절 일치/상태 일치만으로 통과시키지 않는다. 기존 결과의
4/7을 새 정의로 재작성하지 않는다. 통과한 네 유형도 회귀 대상에 포함한다.

구현 전 체크리스트 표를 작성한다: 질문의 명시 요청 / 기존 필수 항목 / 유용한
진행 / 선택 설명 / 미확인 결과 / 필요한 증거 수준. README의 기술명과 일상
질문의 진행 세부를 필수로 둔 것이 질문 의도에 맞는지는 별도 논점으로 표시한다.
**기본은 v1 유지**다. 완화/질문 수정이 필요하면 사용자에게 변경 이유와 v2안을
제시해 명시적으로 결정받는다. 그 결정 없이 항목을 빼거나 후속 단계로 우회하지 않는다.

금지: v1의 정답·필수 항목·실제 source ID를 모델의 질문 분해, 검색, 문맥 선택,
출력 생성에 넣기. 검토용 정답 표는 평가 경로에서만 읽는다.

## 3. 먼저 로컬에서 검증할 내부 계약 후보

일반 답변의 자유 서술 answer와 별도 citation_ids 대신 **주장 목록에서 공개 응답을
조립하는 단일 호출 후보**를 만든다. 별도 최종 서술 모델이나 자동 재시도는 없다.
필드명과 세부 상한은 구현 전 합성 payload 크기 검사로 확정한다.

- 요청 부분: 질문에서 모델이 식별한 1–3개 부분. 고유 번호, 80자 이하 문구,
  확인/미확인 선언을 가진다. 지침은 연관 하위 질문을 최대 3개 단위로 묶되 핵심
  요청을 누락하지 않도록 요구한다. 파서는 3개 초과를 OUTPUT_INVALID로 거부하며
  `[:3]`으로 자르지 않는다. 모델이 핵심 요청을 빼먹은 경우까지 잡지는 못한다.
  정답 표를 주입하지 않는다. 질문 분해 자체가 빠지거나 틀릴 수 있어 자동 완전성
  증명으로 취급하지 않는다.
- 주장: 0–6개, 각 150자 이하. 요청 부분 번호, 종류(직접 답/직접 진행/배경),
  문장과 근거 목록을 가진다. 전체 근거 참조 발생은 최대 8개로 제한한다.
- 근거: 제공된 정수 ID와 해당 제공 본문에 존재하는 비공백 구절(각 120자 이하).
  원문을 바꾸거나 요약문을 가짜 원문으로 저장하지 않는다. 인용 앵커는 기존의
  소유권/버전/field/start/end/hash로 유지한다. 메타데이터는 출처 식별만 지원하며
  행동·채택·완료·사용의 증거로 승격하지 않는다.
- 미확인: 요청 부분 번호당 최대 1개, 총 0–3개/각 140자 이하. 한 부분의 잔여
  미확인 범위를 질문 언어의 완결된 한 문장으로 정리하고 무엇을 확인할 수 없는지
  명시한다. 새 긍정 사실을 끼워 넣지 않아야 하며 이 점도 의미 검토 대상이다. 관련 없는
  추가 검증을 요구하지 않는다. 사용자 채택 보고와 독립 코드 검증을 구별한다.

합성 예제는 실제 7건과 다른 주제/명칭/ID로 작성한다. 동일 모델을 한 번 더
호출하는 요약/비평 단계, 출처별 할당량이나 사례별 예외 규칙은 도입하지 않는다.

### 공개 결과 조립과 형식 검사

1. 허용 키/타입/개수/길이, 유효한 요청 부분 번호, 중복 참조, 제공된 ID만 사용했는지
   검사한다. 각 출력 주장에 근거가 필요하다. 구절은 **제공된 본문 그 자체**에서
   정확히 찾으며 다른 문맥/전체 기록/현재 버전으로 확장하지 않는다. 공백·유니코드를
   임의 정규화해 불일치를 숨기지 않는다. 여러 번 나오는 구절은 일치 여부만 검사하며
   유일한 위치를 확인한 것처럼 새 offset을 만들지 않는다.
2. 각 요청 부분을 다음 표대로 검증한다. 직접 진행만으로 최종 결과의 확인 선언을
   충족시키지 않는다. 진행 자체를 묻는 질문의 진행 사실은 그 질문의 직접 답이다.

   | 요청 부분 선언 | 허용 조합 |
   | --- | --- |
   | 확인 | 해당 번호의 직접 답이 1개 이상이고 미확인은 없음 |
   | 미확인 | 해당 번호의 미확인이 정확히 1개, 직접 답/진행은 0개 이상 |

   동일 부분의 일부 직접 답/진행과 잔여 미확인은 정상적인 조합이다. 배경만 있는
   부분도 반드시 미확인을 가져야 한다. 확인 선언+미확인 공존, 직접 답 없는 확인,
   미확인 선언의 설명 누락, 참조되지 않은 부분/알 수 없는 부분 번호는 출력 오류다.
   유효 구조에서 배경은 공개 답변/인용에서 제외한다. 직접 답/진행이 0개이면
   insufficient, 1개 이상이고 어느 부분이라도 미확인이면 partial, 모든 부분이
   확인이면 supported로 조립한다. **주장 0개+모든 부분 미확인**도 정상 insufficient다.
   이때 직접성·질문 분해·확인 여부는 모델 선언이므로 정확성을 보장하지 않는다.
3. 공개 answer는 통과한 직접 주장과 미확인 문장만으로 결정적으로 조립한다.
   별도의 자유 서술을 붙이지 않는다. citations는 실제 렌더링한 주장들의 ID 합집합이며
   현재 1–5개 제한을 유지한다. 불필요한 모든 선택 근거를 일괄 인용하지 않는다.
   insufficient는 모델의 자유 미확인 문구를 출력하지 않고 짧고 고정된 범위 한정
   안내와 빈 citations를 반환한다. 직접 주장들은 순서대로 줄바꿈으로 연결하고,
   미확인 완결문도 같은 방식으로 붙인다. 서버가 다른 언어의 접두사나 새 자유 서술을
   더하지 않는다. 요청 부분 문구/원문
   구절/배경은 공개 answer에 중복 렌더링하지 않는다.
4. 조립 길이는 최대 `6×150 + 3×140 + 8(줄바꿈) = 1,328자`다.
   형식별 최대치를 동시에 채운 유효 구조도 1,500자 이내여야 한다. 렌더링 서식이
   바뀌면 이 계산과 합성 경계 검사를 함께 갱신한다.
   완성 answer 1,500자/참조 수를 방어적으로 검사한다. 초과 시 자르거나 조용히 주장을 버리지 않고
   ANSWER_OUTPUT_INVALID로 거부한다. 유효 usage는 먼저 spent 정산하고 원본 실패를
   보존한다. 같은 요청 재호출·몰래 상태 수정·기존 구형 응답의 성공 호환은 없다.

현재 status 선언을 믿는 계약을 새 선언으로 포장하는 것만으로 성공했다고 하지 않는다.
예컨대 ‘문서를 검토했고 실행은 안 했다’는 구절을 모델이 직접 운영 진행으로
잘못 분류하면 구절 검사는 통과할 수 있다. 그 결과는 실제 의미 평가에서 실패다.
각 주장과 구절을 직접 대조할 수 있다는 것이 이 후보의 검증 가능한 개선이다.

## 4. 크기·모드·호환성 게이트

현재 가장 큰 동결 요청은 14,317 bytes로 14 KiB까지 여유가 19 bytes뿐이다.
새 schema/지침을 추가한 채 기존 근거를 그대로 넣을 수 있다고 가정하지 않는다.

첫 코드 작업은 새 계약의 payload/응답 합성 예제와 크기 보고서다. 중복 필드를
교체하고 지침을 간결하게 만들어 일반 5사례의 기존 전체 문맥이 그대로 들어가는지
검사한다. 본문/근거를 잘라 넣거나 인용에 필요한 문맥을 평가 정답으로 골라 빼지 않는다.
공유 구성 함수를 사용하는 추천/준비/실제 전송의 bytes가 같아야 한다.
새 일반 5사례 중 하나라도 schema/지침 교체 후 원문 무절단 기준으로 14,336 bytes를
넘으면 이 단계에서 중단하고 대안을 보고한다. 비교를 진행하려고 그 사례를 빼지 않는다.

초기 출력 512토큰도 임시 고정값이었다. 6주장/8구절/미확인 최대치를 동시에 생성할 수
있다고 가정하지 않는다. 합성 상한의 토큰 용량을 로컬에서 검토하고, 확실한 토큰
계수가 없으면 문자수/4를 안전 상한으로 쓰지 않는다. 512가 부족하면 선택지는
계약의 중복 축소 또는 별도 출력 상한/비용 제안이다. 자동 상향하지 않는다.
초기 중단 규칙은 입력 14,336 bytes와 출력 512토큰 양쪽에 적용했고 첫 검사에서
구현을 중단했다. 이후 위 명시 지시로 일반 4,096 후보의 **로컬 구현**을 재개했다.
입력 한도는 그대로이며 실제 출력 용량/schema 수용은 미검증으로 남긴다.
이 로컬 변경을 유료 실행 승인이나 용량 검증 통과로 해석하지 않는다.

일반/회고/과거 모드를 명시적으로 구분하고 각 schema/parser 조합을 고정한다.
잘못된 모드·구형 일반 응답을 자동 감지해 수용하지 않는다. 회고의 줄별 ID 형식과
서울 날짜, 과거 답변의 수집 cutoff 의미를 보존한다. 공통 config hash는 실제 적용
계약/렌더러/모드 버전을 포함하고 이전 프로토콜을 전송 전에 거부한다. DB 변경은 없다.

## 5. 수정 범위와 로컬 검증

후보 파일은 `answer_transport.py`(모드별 schema/parse), 작은 주장 검증/조립 모듈,
`answer_call.py`(명시 모드/반환 연결), `answer_evidence.py`와 준비/비교 도구(동일
요청 구성·digest)다. public AnswerResponse를 유지해 UI/타입 변경은 기본 제외한다.
실제로 변경이 필요하면 범위와 이유를 먼저 문서에 반영한다.

| 합성 검사 | 기대 결과 |
| --- | --- |
| 두 원문에 나뉜 사실 두 개 | 각 주장/근거가 유지되고 렌더링된 근거만 공개 인용 |
| 사용자 채택 보고 + 후속 요청 | 채택 보고 회수, 후속 요청을 완료로 만들지 않음 |
| 추천·문의 진행 + 최종 결과 미확인 | 진행과 미확인을 함께 렌더링하는 partial |
| 배경만 있는 유효 구조 | insufficient/빈 인용; 배경을 답변에 섞지 않음 |
| 주장 0개 + 모든 부분 미확인 | 억지 배경 생성 없이 insufficient/고정 안내/빈 인용 |
| 같은 부분의 일부 직접 답/진행 + 잔여 미확인 | 정상 partial; 충돌로 거부하지 않음 |
| 배경만 있는 부분에 미확인 없음·확인 선언+미확인 | 부분별 누락/충돌로 출력 오류 |
| 구절은 맞지만 주장을 뒷받침하지 않는 예제 | 형식 검사 통과 가능성을 명시하고 의미 평가에서는 실패 |
| 모르는 ID·없는 구절·빈 구절·중복/초과·빠진 요청 부분 | controlled output error, 잘림/재시도 없음 |
| 14 KiB/일반 4,096·회고/과거 512 경계·한글/다중바이트 입력 | 정확한 요청 bytes와 출력 상한 처리 확인 |
| 6주장×150자 + 3미확인×140자·요청 부분 4개 | 최대 조립 길이 1,328자 이하; 부분 4개는 절단 없이 거부 |
| 구형 일반 응답·다른 모드 응답 | 거부; 올바른 회고/과거 입력은 기존 동작 유지 |
| 동의 없음·다른 사용자·삭제·권한 회수·버전 변경 | 전송 차단, 기존 소유권/정책 보호 유지 |
| 유효 usage 후 출력 거부·원본 캡처 실패 | 실제 비용 보존, 새 dispatch 없음, 미확정 보수 처리 |

이 표의 채택/진행 내용은 로컬 조립기의 주어진 합성 입력 동작 검사다. 모델이 실제로
그렇게 분류/회수한다는 테스트로 보고하지 않는다. 본문·개인 원문을 Git/일반 로그에
저장하지 않는다. 실제 자료 대조는 기존에 허용된 문맥/범위 안에서만 수행한다.

관련 테스트 → 전체 백엔드 → diff/요청 digest/모드 회귀 검사를 실행한다. 공개 응답의
텍스트 조립이 바뀌므로 mock 응답 기반 frontend answer 표시 테스트도 수행한다.
프론트 코드를 바꾸면 lint/build까지 실행한다. 기존 테스트 775개의 숫자만 맞추려고
의미 실패를 합성 성공으로 교체하지 않는다.

## 6. 다음 유료 검증의 준비 순서 (현재 실행 승인 없음)

1. 로컬 게이트 후 새 내부 계약과 v1 기준을 고정하고, 기존 일반 5건+회고/과거 2건을
   같은 Luna로 한 번씩 비교할 **7답변 고정 문맥 진단**을 준비한다. 새 검색 embedding은
   필요 없다. 원본 본문은 그대로, 추가 schema/주장/구절/모드 및 설정 hash를 검토한다.
   모델을 함께 바꾸지 않으며 구형 기준선은 ‘과거 기준선’으로 명시한다.
2. 실행기를 먼저 합성 검사한다. 모델별 저장 단가, 개별 예약/총 상한, 원본 보존,
   동일 입력, 배타적 실행 표식/새 요청 ID, 정책/원문 전송 직전 대조, 재실행 거부를
   확인한다. 그 후 정확한 요청·필드·구절 수·입출력 상한·가격·비용표와 단계별
   중단 조건을 한 번에 제시해 **별도 승인**받는다. 현재 금액/회수 승인은 재사용하지 않는다.
3. 승인 후 고정 사례는 각각 한 번만 실행한다. 독립 품질 실패는 기록 후 계속하되,
   출력 오류는 원본/진단/유효 정산이 보존된 경우만 계속한다. 범위/설정/가격/예산/
   권한/버전 변경, provider/schema/auth 거절, DB/네트워크 오류, 신규 미확정 과금은
   전체 중단한다. 생략·미전송은 미검증이며 재호출하거나 성공 사례만 선별하지 않는다.
4. 원문 기반으로 사실 회수·주장별 인용·미확인/상태·귀속·실비·지연을 각각 평가하고
   기존 필수 조건 전체 통과 여부도 보고한다. ID/구절 일치만으로 의미 통과를 인정하지
   않는다. 실패하면 해당 프로토콜을 닫고 원인을 분석한다. 바로 모델/프롬프트를 바꿔
   같은 승인으로 다시 보내지 않는다.
5. 진단이 통과한 뒤에만 **자동 검색부터 답변까지** 기존 7건의 별도 범위를 준비한다.
   검색/자동 선택/생성 실패를 구별하고 이미 통과한 날짜·과거 시점을 회귀 확인한다.
   변형/반복/새 일반화 사례는 이후 별도 제안이다. 알려진 사례로 튜닝한 결과를
   미공개 자료의 일반 품질/반복 신뢰성으로 주장하지 않는다.

## 7. 완료 조건과 커밋 경계

- 로컬 완료: 새 계약/모드별 조립과 보호 경계 테스트 통과, 원문을 보존한 크기 보고서,
  미전송 검토표/실행기 합성 검사 완료. 실제 의미 품질은 여전히 미검증으로 표시한다.
- 실제 진단 완료: 별도 승인 실행과 전 사례 직접 평가. 실패도 작업 결과이며 제품
  품질 완료는 아니다. 자동 검색 흐름과 [ROADMAP.md](../../../ROADMAP.md)의 Phase 3.3 exit는 별도로 남는다.
- 커밋 제안: (1) 계약/검증/조립 및 모드 테스트, (2) 준비/실행기 바인딩·비용/보존 검사,
  (3) 실제 실행 결과 문서. 각각 동작 가능한 경계에서 검증 후 커밋한다.

계획 리뷰에서는 이 문서만 수정하며 구현이나 추가 유료 실험을 수행하지 않는다.
